## [0.10.0] - 2026-10-31

### Changed

- When `safari start` or `lab up` replaces a device session whose lab tab may still be on the phone (after a taint, or a session that died), the step that asks the owner to close that tab by hand is now in the top-level `human` as well as in `previousTab` (issue 103). Agents relay `human`, so the step is no longer easy to miss; it comes before the keyboard step when there is one. The lab still never closes a tab it can't confirm is its own: the owner chose this over widening the start-time tag check to the old tab (2026-10-31). AGENTS.md, the README and the skill say to relay it.

### Fixed

- `safari shot --page` failed on a heavy page with "WebDriver POST …/execute/sync got no answer in 10s (Appium … may be busy or stuck)" (issue 98; seen 2026-10-27 on the iPhone over cable on old.reddit.com and sh.reddit.com, while the session stayed good). The 10 s that ran out was not a page script's: it was the read of Safari's native UI tree (`mobile: source`, built by WebDriverAgent from the accessibility snapshot), which finds where the page sits on the screen and took longer on a big page. That lean read, shared by `tap`, `swipe`, `shot --page` and `shot --element`, now has its own limit of 30 s (`WAIT.treeMs`; it had the general 10 s), and `ui`'s full tree keeps its 60 s. When either runs out the error says so: "Safari's screen layout (its UI tree) did not come back within 30s; a heavy page makes it slow. The session is still good: `safari wait --settled` waits for a busy page to calm down". The read is not sent again, since WebDriverAgent goes on building the tree and a second read would wait behind it.

- On the iPhone a second `safari open https://www.reddit.com/` failed with `needs: tab` "the lab's tab did not answer within 10s", and the session stayed `usable: false` with the lab's tab in front (issue 104; seen 2026-10-27 over cable). Nothing marked the session unusable: `lab status` calls a session usable when it answers, and Appium runs one command per session at a time with no limit of its own on a page script, so every later request waited behind the script that got no answer. On the phone `open` sends five scripts to the lab's tab (the page's state before, `location.replace`, the probe and mark that put the marker back, the reads until the new page is complete, and the console and network collectors), and each had 10 s (`WAIT.tabMs`) while a page that is loading is busy. Each script of an `open` or `refresh` navigation now gets up to 30 s (`WAIT.timeoutMs`; the polling reads and the re-mark get what is left of their 30 s, never less than 10 s), and so do the read of the address right after the load, the `--storage` write and the collectors put back when the lab follows its tab to an allowed host; `--reinject`, `--wait-for` and `--settle`, which run once the page has loaded, and every other command keep 10 s. After a script (or the re-mark's probe or mark) got no answer the lab records the time (`deviceTab.waitingSince`, cleared by the next script that is answered), and a later read that gets no answer says "Appium is still waiting on a script the lab sent to its tab Ns ago, which got no answer: the page is busy, or the tab is not showing. Nothing else runs until it answers; if it has not within a minute, run `safari start`" instead of the pause text; `lab status` shows `waitingSince` next to `usable: false`. The pause text adds "or the page is busy", and `run.log`'s `safari guard: no answer` line names which of `open`'s scripts it was (`page state`, `navigate`, `reload`, `url`, `storage`, `collectors`; the re-mark's own line already names `probe` or `mark`). Not reproduced live yet.

## [0.9.0] - 2026-10-29

### Added

- **`safari eval` awaits a Promise** (issue 102). A Promise or any thenable returned by the script is now awaited for up to `--timeout <ms>` (10 s by default, 100 to 60000), on both targets: the script parks it in a slot on the page's global and the lab reads the slot every 100 ms through the same guarded script path (there is no async execute on the phone). The output has the value, `awaited: true` and `awaitedMs`. A rejection is `ok: false` with `the Promise rejected: <reason>`, and a timeout or a navigation or reload while waiting is `ok: false` with a message saying so. A rejection reason that is an object is shown as JSON, and any reason is cut at 500 characters; a Promise that times out has its slot removed from the page; a value WebDriver fails to return (a cyclic object, say) is an error that says so (Safari itself returns a BigInt as `null`). An extra argument other than `--timeout <ms>` is now refused with the usage (it used to be ignored). This replaces the `value: null` warning added earlier for issue 102. Checked on the iPhone over Wi-Fi (iOS 27.2) on 2026-10-29: `fetch` in about 0.1 s, a 1.5 s timer, a rejection, a failed fetch, a timeout and a reload mid-wait.
- **`safari inject` says when the page left the document the script ran in** (issue 102). The script sets a mark on the page's global first; for half a second afterwards `inject` checks the mark is still on the page showing, and reports `pageChanged: true` with a `warning` when it is gone (a navigation during or after the run, maybe one the script made). On the iPhone over Wi-Fi (2026-10-29) a script that sets `location.href` was caught 3 times of 3, and a plain one never was.
- **`safari inject --forget <file>` and `--clear`** (issue 100). Every injected file stayed recorded for `--reinject`, so comparing two userscripts for one site made `open --reinject` run both (found when a screenshot showed two scripts fighting over the page). `--forget <file>` drops one recorded file, matched by its resolved absolute path (the key `inject` records; the file need not exist any more), and gives `forgotten` and `remaining`; a file that is not recorded is `ok: false`, lists what is recorded and has it in `recorded`. `--clear` drops all of them and gives `cleared` (a count; an empty list is ok with a `note`). Neither runs anything in the page, so they work with no page open, as long as a session is recorded. They take no other word: `--forget` needs exactly one file, `--clear` none, the two cannot be combined, and any other `--flag` is refused with the usage text, all before anything runs. This is a change: `safari inject -- <file>` and a file whose name starts with `--` used to be taken as files; give such a file as `./--name`. `open --reinject` and `refresh --reinject` add a `warning` naming the files when more than one ran again (joined to an existing warning), pointing to `safari inject --forget <file>`. `safari inject --help` and `bin/safari` document the flags.
- **Hosts the lab may follow its phone tab to** (issue 101; [ADR 0009](docs/adr/0009-follow-allowed-hosts.md)). `safari start --allow-host <host>` (repeatable, up to 10; `lab up` passes it through) names hosts that the lab's tab may go to by itself, such as a login redirect or a short link, which used to taint the run. A host is `name`, `name:port`, an IP or `localhost`, matched exactly for both `http` and `https` (no wildcards, no `www` twin); it is checked before anything runs and kept as `deviceTab.allowHosts`. When the tab's marker is gone and the page is on an allowed host, the guard script answers `3` after one yes/no question and the lab marks the tab again through the same select, probe and mark steps `open` uses, records the origin (so `network` admits it), puts the console and network collectors back (it never re-injects scripts) and runs the command once more behind the strict guard. The output gets `followed`, on a refusal too, and `run.log` a `safari follow:` line. Any other site taints as before (nothing is written into it and nothing is read beyond the yes/no check; no origin test in a page script uses a method the page can patch) and the refusal names the session's hosts (or, with none, says to start with `--allow-host`); a taint drops the list. A reused session takes the union of the hosts and never loses one. `open` and `refresh` accept a redirect to an allowed host. A tab still loading on an allowed host after 30 s is `needs: tab`, untainted, "run the command again". Moving the lab's tab to an allowed host by hand is followed too (the two cannot be told apart). With no hosts the guard script is unchanged. On the simulator the hosts are not stored and the output says it has no tab guard. `parseArgs` takes a list of repeatable flags.

### Fixed

- Every Wi-Fi `lab up --target device` failed at the `tunnel` step on iOS 27.2 (`rsd-failed: ConnectionRefusedError`; issue 111, live 2026-10-28). The tunnel host's check, `pymobiledevice3 remote rsd-info --rsd <address> <port>`, handshakes with the tool's host-id UUID; on iOS 27.2 a handshake with a UUID other than remoted's makes the phone close every service listener on the tunnel. The host now runs `remote rsd-info --native` with `PYMOBILEDEVICE3_UDID` set to the saved phone (it rides the same remoted tunnel and uses remoted's UUID), so the device check, the iOS version and the service catalog for Appium are unchanged. No new pymobiledevice3 version is needed (11.40.2 has it). ADR 0006 has a dated note with the measurements and the rejected alternatives. Checked live on the iPhone over Wi-Fi on 2026-10-29: the full `lab up`, and 10 minutes of use over the tunnel with no drop.

- `safari eval` of a Promise returned `{}` with `ok: true`, and the docs said the owner's userscript extensions may run in the lab's tab (issue 102, seen on an iPhone run, iOS 27.0.1, cable). `eval` now awaits it (see Added). The README, AGENTS.md and the skill now say what was seen: other Safari extensions ran in the lab's tab, the Userscripts app's scripts did not in that run (cause unknown), so test a userscript on the phone with `safari inject`; and that `inject` right after a navigation may run in the outgoing page (seen once), so wait for the page first (`safari wait <css>` or `open --wait-for`).

- `wait --settled` never settled on a feed with lazy images (issue 99; seen on sh.reddit.com: "36 images still loading" with nothing changed for 23 s). The page script judged an unfinished image by its position alone, and an image with no box (`display: none`, a collapsed or `content-visibility` ancestor) measures 0 x 0 at (0, 0), which counts as in view, and a lazy one never loads. Now an unfinished image is waited for only if it is rendered (`getClientRects()` is not empty and `checkVisibility()`, where Safari has it, is not false) and, when it is `loading="lazy"`, has a size and is in the viewport (an eager image with no size yet is still waited for: it may be a picture whose headers have not arrived). The ones left out are counted as `skippedImages`, which every `--settled` output has (also a timeout's, as a number, 0 when none), and the timeout says "N images still loading (M more off-screen or hidden, not waited for)". Checked by tests only; not yet run on a live feed.

- A Wi-Fi tunnel that failed at `rsd-info` said only `rsd-failed`, and its log line was the start of the tool's traceback box (issue 107, live 2026-10-28: two `lab up --target device` runs). `rsdInfo` kept the first 160 characters of pymobiledevice3's output, which are the frame, and dropped the exception line at the end, so refused, timed out and no route looked the same. The host now reduces output that has such decoration (ANSI codes, box-drawing frames, a `Traceback` line, an exception group's `+`/`|` lines) to its exception line (`toolFailure` in `lib/tunnel-host.js`: the last line that looks like a Python exception, else the last plain line; plain text is kept whole, as before), and starts the tool with `COLUMNS=500` so rich does not wrap that line. It logs it, and saves it as a new optional `detail` (at most 200 characters, device ids masked) next to `reason` in `tunnel.json`. The `tunnel` error (`the tunnel host stopped before the tunnel was up (rsd-failed: ConnectionRefusedError: ...)`), `lab tunnel status` and `lab down`'s tunnel step show it. The `tool-exited` reason gets the same reduction. The `tunnel` hint no longer says Xcode should show the phone with a network icon (not confirmed in Xcode 27, as in PR 97); it names a VPN, another network or band, or the phone's Wi-Fi asleep as things to check.

- A `lab up` failure's `then` dropped the flags the run was given (issue 106; seen 2026-10-28: `lab up --target device --allow-host old.reddit.com --url https://old.reddit.com/` failed with `needs: tunnel` and its `then` was a bare `lab up --target device`, so an agent running it as told started a session with no allowed hosts). When `then` is a `lab up`, it now repeats `--allow-host` (each, as normalised), `--url`, `--profile`, `--appearance`, `--orientation` and `--no-focus`, quoted for a shell, in that order; the same for the `then` on a failed step (the simulator cold-start hint). Never `--force` (taking the lease is the person's call). A `then`'s own `--target` and `--resign` stay; a device `then` leaves off `--profile` (it picks a simulator) and a simulator one leaves off the phone-only flags. `or` is unchanged. `quote` moved from `lib/version.js` to `lib/core.js` to be shared.

- The origin tests in the scripts the lab sends into the phone's tab could be answered by a page on another site. The probe and the mark after `open` and `refresh` (and the new follow check) tested `["https://a", ...].includes(location.origin)`, and a page that had patched `Array.prototype.includes` before the lab's script ran could make that true, so the mark wrote the lab's `window.name` token into a page on an unexpected origin before the run was tainted. They are now `location.origin === "https://a" || ...`, with no method call on a prototype the page can patch. The guard script with no allowed hosts is unchanged. A guard answer of `3` that the guard could not have given (no allowed hosts, or the strict re-run) now taints instead of being refused as not understood. The one check `safari start` runs in the page the driver picks before it plants the token, `location.search.indexOf(tag)`, is now `location.origin !== "https://example.com" || location.search !== "?msl-..."` for the same reason: a tab of the owner's that had patched `String.prototype.indexOf` could pass it and be given the token.

- The Wi-Fi setup steps and the `needs: cable` steps no longer tell you to turn on Xcode's "Connect via network". Xcode 15 removed that setting: a phone paired with the Mac over the cable is reachable on the network by itself (checked live 2026-10-27 with Xcode 27.0 on a newly paired iPhone: `lab phone status` said `transport: wifi`, `via: tunnel` after one cable `lab up` and nothing in Xcode). The README, AGENTS.md and the `cable` hint now say to pair once over the cable, then keep the phone on the same Wi-Fi network as the Mac.

- A `devicectl` call that failed with a dropped CoreDevice control channel was `needs: unknown` (issue 81, live 2026-10-24: the first `lab phone focus test` after the phone idled on Wi-Fi; `A connection to this device could not be established. (CoreDeviceError error 4000)`, `ControlChannelConnectionError`; the same command worked when run again). The shared `devicectl` wrapper in `lib/phone.js` now makes a call once more at once (same time limit) when devicectl says the connection to the device "could not be established", but only for callers that pass `{ retry: true }`: read-only calls (`device info`, `list devices`) and ones that set a state idempotently (appearance and orientation, install, uninstall, the Lab Focus shortcut). A Safari launch (`openTab`) and a process signal are never retried, since devicectl's text does not prove the command never reached the phone and a second run would open a second tab. Nothing is retried after a timeout, any other error, or a `ControlChannelConnectionError` / error 4000 / "Connection was invalidated" without that phrase (which may be a drop mid-command). If the retry fails too, or for those other drops, the failure is `needs: cable`, whose `human` steps gain a "run the command again" line, and `runShortcut` reports `cable` rather than `shortcut`. The real text is the fixture `test/fixtures/phone/coredevice-4000-stderr.txt`. The existing `CoreDeviceError 4016` pattern never matched devicectl's real wording (`CoreDeviceError error 4016`, with the word "error"); it now does, as does the 4000 one.

## [0.8.0] - 2026-10-25

### Added

- **Giving back a slot borrowed from sideload** (issue 63; [ADR 0008](docs/adr/0008-slot-lending.md)). The plumbing and the return side of slot lending (the lend step is the next entry). `lib/slot-lend.js` keeps `state.slotLend` (`{udid, phase: lending|lent|returning, at, bin, home, since?, app?, device?, retryAt?, returnFailed?}`, validated; a damaged record names `lab phone slot forget`), written before `slot lend` and before the runner is uninstalled, and `returnSlot()` gives the slot back: it finds the sideload binary first, checks the phone is unlocked and reachable (`lockState`), lists the apps (`xcrun devicectl device info apps`), stops WebDriverAgent's `xcodebuild`, uninstalls `<phone bundle id>.xctrunner` (guarded: never an `io.github.dividedby.free.*` app), checks it is gone, then runs `sideload slot return --udid <saved UDID>` with the record's `SIDELOAD_HOME`; only `reinstalled`, `alreadyPresent` or `nothingLent` clear the record. `lib/sideload.js` finds the binary (`MSL_SIDELOAD_BIN`, which must be absolute and executable, else the record's `bin`, else `PATH`), calls `slot lend|return` (time limits 17 and 22 min, SIGTERM then SIGKILL after 30 s, the lease renewed every minute), reads sideload's envelope and holds the code tables as data (busy, device, owner action, retry; anything not listed is an owner action). A call whose outcome is not known (a timeout, `INTERRUPTED`, output the lab cannot read) is retried after sideload's `retryAfter`, else after 645 s (its longest operation window), counted from the end of the call. A return that cannot finish keeps the record, says it once, and does not count as a failed idle stop. The idle stop retries every tick (not before sideload's `retryAfter`, and, for an owner action, not until a lab command has run); `lab down` gives the slot back when the idle stop is not installed and loaded or the return had started. New: `lab phone slot return` and `lab phone slot forget`, a `slot` step in `lab down` (right after `wda`), `slotReturned` and `slot` in the output of `lab down`, `idleStop.last.slot`, and a `slot` block in `lab status` (`bin`, `lend`, and sideload's `status` while a record exists). `lab phone forget` and `lab phone setup` for another phone are refused while a record exists. `lab service install` passes `MSL_SIDELOAD_BIN` and `SIDELOAD_HOME` to the idle stop (run it again to pick them up).
- **Borrowing a slot from sideload when the phone is full** (issue 63; [ADR 0008](docs/adr/0008-slot-lending.md)). `lab up` for a new phone session has a new `slot` step (after `phone` and the early signing lock look, before the phone settings, tunnel, Lab Focus and session). It lists the phone's apps once (`devicectl device info apps --bundle-id <bundle id>.xctrunner`); with WebDriverAgent missing it builds the runner if there is no build (`buildWda`, now shared with the Wi-Fi launch) and installs it under the signing lock. **installd decides whether it fits**: `sideload slot lend` does not check that the phone is full, so the lab calls `sideload slot lend --udid <saved UDID> --to lab` only after installd refused that install with its free-app limit (never the App-ID-per-week limit, never an unreadable listing, which lends nothing), with the lock released, then installs again. The result gains `slot` (`lent`, `freed`, `alreadyLent`, `dataRestored`, `warnings`) when a slot was borrowed or a record settled. Every sideload answer is data (`LEND_MAP`): `busy` codes stop `lab up` with `needs: busy` and a `retryAt` and keep the record; owner actions are `needs: slots` with sideload's fix as the last `human` line; `DEVICE_NOT_CONNECTED` is `tunnel` or `cable` by transport. The step can take about 17 minutes for the lend, plus the WebDriverAgent build (first time) and up to two installs. A phone `lab up` reuses a lend it holds; a record left in `lending` or `returning` (a crash) with WebDriverAgent on the phone is settled by one `slot return` call, never an uninstall. `lab up --target simulator` gives a stale lend back when the idle stop is not installed and loaded or the return had started (a reported `slot` step, never a failure of `up`). Passed live on a device on 2026-10-25 (acceptance item 41).
- `lib/phone.js`: `appListed`, `uninstallRunner` and `installRunner` (the last for the lend step), `runnerApp` (the scan `profileExpiry` did, now shared), `isAppLimit` (installd's free-app limit, never the App-ID-per-week limit) and `slotsError`. `lib/core.js`: `runAsync` takes `killAfterMs` (default 3 s).

### Fixed

- The `lab up` slot step missed installd's free-app limit when devicectl's message was long, so it never lent a slot (issue 63, live 2026-10-25). The failure text was cut to 400 characters before `classify` and `isAppLimit` read it, and in a real devicectl message the "maximum number of installed apps" sentence comes after that, so the install read as `needs: unknown` and `lab up` stopped instead of calling `sideload slot lend`. `lib/phone.js` now classifies every failed devicectl call on its whole (redacted) text; only the `error` shown is cut to 400 characters. The real stderr is the fixture `test/fixtures/phone/install-free-app-limit-stderr.txt`.
- sideload's app-data counts now reach the lab's `slot` object (issue 63, found in the live Stage 2 run, acceptance item 41). `slot lend` says `dataBackedUp`, `dataFiles` and `dataFilesFailed`; `slot return` says `dataRestored`, `dataFilesRestored` and `dataFilesFailed`. The lab passed on only `dataRestored` and the warnings, so "2 of 13 data files were not backed up" had no count beside it. They now appear in `lab up`'s `slot` (a lend, or a settled record) and in the `slot` of `lab phone slot return`, `lab down` and the idle stop, when sideload gives them. Only booleans and whole counts of 0 or more are passed on; any other type is dropped, and the lab never depends on them.
- The phone's WebDriverAgent runner no longer stays on the phone ("Automation Running") after `lab down`, the idle stop or `safari stop` (issue 86). Stopping the Mac's `xcodebuild` does not end WebDriverAgent's test, so over Wi-Fi the runner kept running. The `wda` step and `safari stop` now ask the runner to shut down first (`GET /wda/shutdown` through the tunnel, 3 s) and give the `xcodebuild` 10 s to exit by itself before SIGTERM; then they read the saved phone's process list (`devicectl device info processes`) and SIGKILL a `WebDriverAgentRunner-Runner.app` process still on it (SIGTERM is answered by a relaunch), and read the list again 5 s later. A runner still there is an error with a `lab down`-again or volume-buttons hint; a phone that can't be listed is a note. The same cleanup runs before the lab starts a new WebDriverAgent. The tunnel host's own stop leaves the phone to `lab down`. A `lab down` that fails there keeps `lastTarget`, so a retry (and the idle stop, which counts it as something still running) reads the phone again.

### Changed

- `lab up` for a new phone session now looks at the signing lock shared with sideload (issue 63) early, as a `signing lock` step, instead of finding it busy only at the `session` step after 8 to 20 s of Appium, tunnel and Lab Focus setup (acceptance item 39, live 2026-10-24). The look is the same non-blocking take, let go at once (`probe()` in `lib/signlock.js`). With `--target device` and no session on record it runs right after `prerequisites`, before Appium starts; with `--target auto` (or a recorded session that turns out dead) it runs right after the `phone` step, which is where the target and a live session are known. Either way it comes before the Wi-Fi tunnel, the phone-settings restore and Lab Focus. If sideload holds the lock, `lab up` stops there with the existing `needs: "busy"` and its `human` line (`failedStep: "signing lock"`, the step found `held by sideload`); no tunnel is opened and Lab Focus is never turned on, and with `--target device` Appium isn't started either (`--target auto` only knows it is the phone after the phone step, so Appium may already be up). A free lock is let go and the run goes on; the real take at the `session` step is unchanged, so a lock that sideload takes in between still gives `busy` there, and Lab Focus is still turned off again. No look when a live session is reused, on the simulator, with no `SIDELOAD_HOME` folder, or with `MSL_SIGNLOCK=off` (which keeps `signLock: "disabled"` and its warning); those runs have no `signing lock` step. An unopenable lock file or a failing helper stops the look with the same errors as the take.

## [0.7.0] - 2026-10-24

### Added

- `sim doctor` reports `phoneDisplay` when a phone is saved: whether this Mac's `xcrun devicectl` has the appearance and orientation commands (their `--help` texts; nothing is sent to the phone). An older Xcode adds `hints.phoneDisplay`; it never makes `ok` false.
- **Appearance and orientation on the iPhone** (issue 27). `safari appearance light|dark|restore|status` and `safari orientation portrait|landscape|restore|status` (landscape is `landscapeLeft`), and `lab up --appearance light|dark --orientation portrait|landscape`. They go through `xcrun devicectl device settings appearance --mode`, `device info appearance` and `device orientation get|set` (Xcode 27; no WebDriverAgent session; argument lists, the saved UDID in `--device`, bounded at 20 s per call, JSON read from `--json-output`), and every change is read back (at most three readings). Live-checked 2026-10-23 on iOS 27.0.1 over Wi-Fi: an open Safari page followed the switch with no reload. iPhone only: a simulator session is refused with a message, and `sim appearance` is unchanged.
- **A restore ledger for phone settings the lab changes** (`lib/phone-restore.js`, `state.phoneRestore`; `pendingRestore` in `lab status`, at the top level and under `phone`; at the top level with a `human` step also when the phone record is gone). One table in `lib/phone-restore.js` describes each kind of setting (appearance, orientation), so a new kind is one entry plus its devicectl adapter. The prior value is read and written down before the change is sent (the change is refused if it cannot be read), an existing entry keeps its prior, and the entry is cleared only after the phone reads back the old value. Put back at `safari stop`, `lab down` (a `phone-settings` step when a record is left behind, after `session`), the idle stop, and the next `lab up` that starts a new session (a live session's changes are left alone); `lab phone restore` does it now and `lab phone restore --forget` drops a damaged record or one whose phone is gone (both are refused while another owner holds a live lease, and take none). A locked or unreachable phone is reported (`phoneRestored: false`, `human`), never a failure of `stop` or `down`, and the record is kept. A value the owner changed by hand meanwhile is left (`ownerChanged: true`). Appearance cannot be read as Automatic: a restore sets back light or dark and says `restoredExactly: false` with a note. Orientation is put back as the upright orientation first, then the flat reading (`portraitUpsideDown` becomes `portrait`, `restoredExactly: false`). With Portrait Orientation Lock on, the phone ignores `orientation set` and its lock flag still reads off, so an unchanged reading fails with "Portrait Orientation Lock is probably on" (when putting back, the record is kept and the advice is to turn the lock off and run `lab phone restore`).

- **Lab Focus during iPhone sessions** (issue 16; [ADR 0007](docs/adr/0007-phone-settings-restore-ledger.md), addendum). `lab up` on the phone now turns on the owner's own Focus "Lab" by running their shortcut "Lab Focus On" (a new `focus` step, immediately before the session is created so the lab's Safari tab is opened after the Shortcuts app it leaves in front), and the same triggers as appearance and orientation (`safari stop`, `lab down`, the idle stop, the next `lab up`, `lab phone restore`) run "Lab Focus Off". A running session is kept as it is, and the simulator never runs it. Delivery is confirmed, not the effect (`focus.verified: false`). The ledger entry records the Off shortcut's name when On runs, and the restore runs that name. A `lab up` that fails after the focus step and before its session opens turns Lab Focus off again (lock-checked; a locked phone keeps the entry and the failed JSON says it is still on), and the idle stop also tries a pending Lab Focus restore when nothing else is running (once per idle period). `lab phone focus test` and `lab phone focus off` check the setup by hand (test runs the On shortcut with the ledger entry written first and says to look for the Lab Focus icon; off runs the Off shortcut and clears the record; both lock-checked, lease-checked, refused with a session open). README ("Lab Focus during phone runs"), AGENTS.md, the skill, CONTEXT.md and ADR 0007 describe it; acceptance item 38 is the live check (unchecked).

### Added

- Idle stop (issue 40): a lab nobody has used for 15 minutes (`MSL_IDLE_MINUTES`, 1 to 1440) is stopped by itself, so Appium and the phone's WebDriverAgent no longer run until someone runs `lab down` (they did on an 8 GB Mac under swap). `lab service install` now also installs a second LaunchAgent, `com.dividedby.msl-idle`: no `KeepAlive`, no `RunAtLoad`, `StartInterval` 300, nothing resident and nothing listening, log `~/Library/Logs/msl-idle.log`, running `lab down --idle`. `--no-idle-stop` skips it and removes an installed one; `lab service uninstall` removes both; a failure installing it is reported as `idleStop.error` and does not fail the service install. - Interrupts (issue 41): `sim`, `safari` and `lab` handle SIGINT, SIGTERM and SIGHUP (`lib/interrupt.js`). The signal ends the wait the command is in (a `sleep` or a WebDriver request), so its own cleanup runs, and the output is one JSON object with `ok: false` and `interrupted: "<SIGNAL>"` (no failure screenshot or page source) and exit code 130, 143 or 129. The picture is cut in memory by a small PNG reader and writer on `node:zlib` (`lib/png.js`; no `sips`, no dependencies): 8-bit non-interlaced RGB and RGBA, all five row filters, checksums verified, up to 16384 px a side and 100 megapixels; a palette, grayscale, 16-bit or interlaced PNG is refused by name. - iPhone support. `lab phone setup --udid <UDID> --team <TEAMID> [--bundle-id <id>]` saves the phone, `lab phone status` asks it live (reachable, transport, locked, Developer Mode, signing expiry as `wdaHoursLeft`) and `lab phone forget` removes the record. Every device failure ends in JSON with a `needs` value (`setup`, `xcode-account`, `keychain`, `developer-mode`, `trust`, `unlock`, `passcode`, `cable`, `resign`, `slots`, `tab`, `service`, `unknown`), the `human` steps, the command to `then` run, and `or: lab up --target simulator`. See the README's Real iPhone section.
- `--target auto|device|simulator` on `lab up` and `safari start`. `auto` uses the saved phone when it is reachable, unlocked and in Developer Mode, the simulator when no phone is saved, and otherwise refuses with a `needs` value rather than falling back silently.
- `lab up` and `lab down` on the phone: `lab up` adds a `phone` step (reachability, signing; WebDriverAgent is signed again when under 24 hours are left, or with `--resign`), and `lab down` closes the lab's tab, ends the session, stops the WebDriverAgent `xcodebuild` and skips the simulator steps. `lab status` shows the saved phone.
- Tab guard and privacy on the phone: the lab opens and pins its own Safari tab, checks it before and after every command, refuses (`needs: tab`) when it cannot confirm it, reads no other tab (its only look at a page it hasn't confirmed is one yes/no check at start that the attached page is its own tab), refuses off-site redirects, and closes (or blanks) its tab at `safari stop` and `lab down`. Failed commands save no screenshot or source from the phone.
- On the phone `safari network` is cut to the sites the lab's tab visited and rebuilt from a fixed list of fields (`outside` counts what was left out), and `safari console` reads the lab's own in-page collector. (`network` is now the page's Resource Timing; see Changed.)
- `safari keys` on the phone reports `textChecked` and `caseChanged` (only the case differs: the keyboard autocapitalises) and, when the text was not compared, `textSkip`; anything beyond case fails.
- Appium's log redaction: the LaunchAgent starts Appium with `--log-level info --log-filters` so page URLs and titles stay out of `msl-appium.log`; device sessions require that service (`needs: service`) and `lab service status` reports a plist without it.
- `lab down [--force] [--keep-service]` ([ADR 0004](docs/adr/0004-lab-down.md)): stops everything the lab started, so the Mac's resources are free when nobody is testing. In order (`lease`, `session`, `wda`, `simulator`, `window`, `safaridriver`, `appium`, `release`, each with what it `found` and `did`): checks the lease (another owner's live one is refused like `lab up` does, `--force` takes it); ends the Safari session; shuts the Claude iPhone down by its UDID; quits Simulator or Device Hub (asking the app, never killing it) only if `sim boot` or `lab up` opened it and no simulator is booted; stops the `safaridriver` the lab started for a `--device` session; stops Appium (the LaunchAgent is disabled, so it doesn't start at the next login, then booted out, and the plist stays; without the service, a recorded Appium pid is SIGTERMed only after `ps` shows it still runs Appium); releases the lease. `--keep-service` leaves the Appium service running. A recorded pid is only signalled when its command line is Appium or `safaridriver` itself, not any command that mentions the name (`vim appium.md`). Best effort: a step that fails is reported, the others still run, the result is `ok: false` and the lease is kept. A second run does nothing. `lab up` loads the service again.
- `lab service install [--log-level info|debug]` (default `info`) picks the Appium service's log level; `lab service status` reports it as `logLevel`. The redaction `--log-filters` are in the plist at both levels, and the device-session check (`needs: service`) and `status` issues accept `debug` with the filters and still refuse a plist without them. Switch back with `lab service install`.
- The state records `windowApp` (`Simulator` or `Device Hub`) when `sim boot` or `lab up` opens a window that wasn't running before.

- `lab down` has a `wda` step before `simulator`: it stops the WebDriverAgent `xcodebuild` Appium started (a child of Appium's pid, with the Claude iPhone's UDID and a path in the msl-appium folder) and a `simctl diagnose` for that simulator, each only after `ps` shows the pid still runs that.

### Changed

- **Run `lab service install` once more.** Appium logs every request body at info level (cut at 1024 characters), and the log-filter rules covered only URLs and titles, so the text of `safari type` on the simulator and, on the phone, `keys` characters, were readable in `~/Library/Logs/msl-appium.log` in the `args` of a script call or the `text` of an element-value call. The rules now also mask, to the end of the line, everything after `"args":` or `args=` / `args:` (request bodies; at debug level `Calling X() with args:` and the remote debugger's `Executing atom '…' with 'args=…'`, which is not cut), the body of an `/element/<id>/value` request, and the body of a proxied request (`Proxying [...] with body:`, which carries the keys sent on to WebDriverAgent), so a quote, bracket or a body cut at 1024 characters cannot end a match early. The rules file is compared with the one this lab writes: `lab service status` lists "the log-filter rules are older than this lab's" as an issue, `safari start` and `lab up` on the phone refuse with `needs: service` until `lab service install` is run, a simulator start through the service refuses the same way, and `open --storage` refuses (also when the service names no rules file) before it does anything. An Appium the lab starts itself (no service installed) is now started at log level `info` (Appium's default is debug) with the same rules; one that was already running keeps what it was started with until it is stopped (`safari stop`, `lab down`). An Appium started by hand, or reached through `MSL_APPIUM_URL`, is not checked, so `type` text may be logged there; `open --storage` is refused for it. This holds at the default `info` level; `--log-level debug` also logs command results, including text read back from fields (what `keys` reads), so use it only for debugging and delete the log afterwards (storage values are not affected: the write returns only a count).
- **Secrets can't leak through a mistyped argument, a failure or a stale service.** `open` and `refresh` read every word in one place and refuse what they don't take by its position (`open: argument #3 is extra (open takes one URL)`), never by echoing it: `--storage=key=value` (the pair goes in the next word), any other `--flag=value`, an unknown or misspelled flag (`--Storage`, `-storage`, a bare `--`), a second address, a repeated `--wait-for`/`--timeout`, and a value that is missing or looks like `--storage`. Before, some of these printed the value into the output and `run.log` (and saved `fail.png`/`fail.html`), and some dropped it silently and opened the page without it. `refresh` refuses `--storage` in any spelling and takes no address. The shared flag parser no longer prints a word it can't name (`--x=…` is refused; a flag is named only when it looks like a name). `keys` names an unknown `--word` by its position. Text typed with `type` or `keys` stays out of every message: `keys` failures say `character #3 did not land after 3 attempts; 2 characters were typed before it` (they used to quote the character and the text typed so far), and once the first character has been sent a `type` or `keys` failure saves no `fail.png`/`fail.html` and says nothing the page or Appium wrote about it (before anything is typed, the usual artifacts are kept). The page's name for a refused `--storage` write is shown only if it is `QuotaExceededError`, `SecurityError`, `InvalidStateError` or `TypeError` (else `Error`), and any other failure of that page command is a fixed message. After the write the page can still repeat what was written (its title, its own errors, the screen), and values are in your shell history and the process list: use test flags and dummy tokens, never real secrets.
- **The service is checked as it runs, not only as its file reads.** `type` and `keys` now refuse with `needs: "service"` when the LaunchAgent is installed and its rules are stale (before any request), as `start` already did. A running service must have started after its rules file was last written, else it may hold older rules (`the running Appium (pid N) started before its log-filter rules were written`; checked for `type`, `keys`, a simulator start, `--storage` and the phone); a plist whose arguments can't be read, that starts Appium without `--log-filters` at log level `info` or `debug`, or that names no rules file is refused for the simulator too (it was waved through). `lab service install` writes the new rules file only after launchd has let go of the old service, so a bootout that doesn't finish no longer leaves a file that looks current while the old process still runs the old rules.
- `safari click`, `type` and `tap` now refuse extra positional arguments: `click a b` used to ignore `b` and `type input hello world` typed "hello"; both are errors now (`one selector only`). For `type`, a text that is exactly one of the new flags (`--text`, `--nth`, `--contains`, `--shadow`) is now read as a flag: type it after `--` (`safari type input -- --text`). Any other `--word` is still typed as text. `type --text` matches visible text, so it usually finds a label or container, not an `<input>` (inputs have no `innerText`): use a css selector for fields.
- The phone does not auto-lock while a lab session runs (WebDriverAgent keeps it awake) and locks normally after `lab down`: always `lab down` (battery).
- Switching Safari tabs mid-session only pauses the session (native actions are refused with `needs: tab` until you switch back); the session ends, and `safari start` opens a fresh tab, when the lab's own tab changes under it (navigated by hand, closed, replaced). Measured on the iPhone 2026-10-18; the docs said the switch itself ended it.
- `safari start --device <UDID>` is an alias for `--target device` and must name the saved phone. `lab status` shows the saved phone. `sim` commands refuse while the Safari session is on the iPhone.
- A cold `lab up` after `lab down` no longer fails. The session create (up to 420 s) went over `fetch`, whose 300 s headers limit fired first and was reported as "not reachable"; waits over `WAIT.fetchLimitMs` (280 s) now use `node:http`, and fetch's own header or body timeouts are reported as "got no answer in <n>s (Appium may be busy or stuck)". A create that fails with "remote debugger did not return any connected web applications" (Web Inspector shows no pages for about 30 s after a cold boot) is tried once more, and the step's `did` says so. A cold `lab up` can take 4 to 10 minutes on a loaded 8 GB Mac; `lab down` frees about 3 GB, so for a short break use `safari stop`.
- ADR 0003's always-on Appium is now "on until `lab down`" ([ADR 0004](docs/adr/0004-lab-down.md)). `lab service status` words "installed but not loaded" as normal after `lab down`. The skill and README tell agents to finish with `lab down`.
- The phone's `safari network` reads the lab page's own Resource Timing instead of Appium's network log (`showSafariNetworkLog` is no longer set, and the phone may no longer ask Appium for `safariNetwork`). Output: `count`, `requests` (`method` always `null`), `outside`, `origins`, `dropped: 0`, and when they apply `truncated` (more than 500 waiting: read again), `lost` (past the collector's 2000) and `early` (the browser's 250-entry buffer was full at install). `network.json` keeps `name` (the URL), `initiatorType`, `startTime`, `duration`, `transferSize`, `encodedBodySize`, `decodedBodySize`, `responseStatus` and `nextHopProtocol` and nothing else. There is no `copies`. Not available: methods, headers, bodies, statuses (`responseStatus` and `method` were `null` on every entry measured on iOS 27.0.1), sizes of another site's requests that send no `Timing-Allow-Origin` (0), and probably requests that leave the page's own JavaScript world (`GM_xmlhttpRequest`). The simulator's `network` is unchanged; its `dropped` counts byte-identical copies and WebDriverAgent's own traffic. The docs say what each field means, and not to `eval` the page's timing entries on the phone (it prints every site the page talked to).
- `safari console` on the simulator reads Safari's log through Appium; on the phone it reads the lab's in-page collector (messages from before it was installed are missed). The README said the former for both.
- Docs: `AGENTS.md` section 9, "Report what you find (bugs, features, docs)": how an agent in another repo notes lab problems in `lab-feedback.md` and files them as issues (de-duplicate, one OK from the owner, privacy rules, body template). The skill and README link to it.
- Docs: simulator taps measured 6 to 19 s on a cold simulator on an 8 GB Mac; the 0.4 s `tap` pause leaves out the native tree reads. `tap` scrolls an off-screen element into view (`scrollY` changes).

## [0.3.1] - 2026-10-15

### Added

- `safari console` and `safari network` say when they may have lost entries: Appium keeps the last 5000 raw entries of each log and drops older ones silently. When the raw log reached 5000 the output gains `truncated: true`, `copies` (the most times one message repeated, about one per listener Appium has added) and a `note` saying to read more often or restart the session. Nothing is added otherwise.
- `safari keys --no-verify`: sends each character once and checks nothing (the previous behaviour; the result has `verified: false`). `safari keys` refuses any other `--flag`; put `--` before text that starts with `--`.

### Changed

- Appium's idle wait is off (`waitForIdleTimeout` 0, set through the session's settings, best effort with a warning on failure): WebDriverAgent waited up to 10 s before and after every native action for Safari to idle, which it never does in the simulator, so each tap or key cost about 20 s. `safari start` and `lab up` set it on new and reused sessions, so run either once after updating. `tap` pauses 0.4 s and `swipe` 0.6 s afterwards for the page to settle.
- `safari keys` runs entirely in the page (web context): the keyboard check, the key presses (`mobile: keys` goes to WebDriverAgent whatever the context) and the per-character reads all stay there, so a `keys` run adds no console or network listeners to Appium. Before, it switched to the native layer and back once per character, and every such switch added a listener, so each message arrived many times over and Appium's 5000-entry buffer filled quickly. Backspace still leaves the page for one native round trip per press (it clicks the keyboard's delete key). `mobile: keys` deletes nothing with `"\b"`, `"\u007f"`, `"\uE003"` or `"\u0008"` (tried live), so there is no switch-free Backspace. `tap`, `swipe` and `ui` still switch (issue 7).

### Fixed

- `safari keys` no longer drops characters silently. Each character is checked to have landed (the focused field's length changes), waited for up to 1.5 s (a press has arrived 0.9 s late), sent again up to twice if it still hasn't, and the command fails with `ok: false` naming the character and its index when it still doesn't land, instead of reporting `ok: true`. The result gains `retries` and `unverified` when they are not zero. Not checked: Return, a character in a field at its `maxlength`, Backspace in an empty field, and anything once focus has left the field (these are sent once). A resend that doubled a late press (the field grew by more than one character) fails too instead of reporting `ok: true`; Backspace is not checked for that. Over a selected range the first character is sent once (it replaces the selection, so the length may fall) and is never resent. A field that refuses a character on purpose now fails. A marker `keys` leaves in the page if it is killed is cleared at the start of the next run.
- `safari tap` and `swipe` on zoomed pages. On a page zoomed in (`initial-scale=2` or pinch) and scrolled, the calibration probe was not at the visible corner, so taps landed off screen or on the wrong element and swipes scrolled nothing, all reported as `ok: true`. The probe is now placed at the visual viewport's offsets so it is on screen, its measured client position (`getBoundingClientRect`, which is not where it was placed when zoomed) anchors the mapping to its native position, and `area` is the visible part of the page. The scale comes from `visualViewport.scale` instead of the probe's size, which the native tree rounds to whole points (taps drifted up to about 6 px, so thin targets were missed on zoomed-out pages). `calibration` gains `scaleFrom: "visualViewport"` when it is used; without `visualViewport` the old probe-size scale applies.
- `tap` and `swipe` refuse, with a message saying how to recover, when the calibration probe is off the screen (checked against `/window/rect`) instead of acting somewhere wrong.

- `bin/lab` (Phase 2, [ADR 0003](docs/adr/0003-launchagent-health-and-lease.md)): `lab up [--url] [--force]` checks and repairs, step by step (`lease`, `prerequisites`, `appium`, `simulator`, `session`, `open`), reporting what it found and did; recovers a killed Appium, a killed Safari, a shut-down simulator and a deleted session; a second run changes nothing. `lab status` looks at the same things without changing anything. `lab release [--force]`.
- `lab service install [--replace] | uninstall | status`: Appium as a per-user LaunchAgent (`com.dividedby.msl-appium`, `127.0.0.1:4723`, restarted by launchd, log in `~/Library/Logs/msl-appium.log`). The plist records a Homebrew-stable `node` path (`/opt/homebrew/bin/node` or a non-Cellar `node` symlink on PATH, not the versioned Cellar path) and `status` reports it; after a node major upgrade, run `install` again.
- Simulator lease: a lease file in the state dir (`{owner, since, expires}`, 15 minute TTL, `MSL_LEASE_TTL`) taken or renewed by every `safari` command and by `sim boot`, `open`, `tap`, `type`, `scroll`, `swipe`, `appearance`, `statusbar`, `shutdown` and `reset`. Another owner is refused with who, until when, and how to take over; an expired lease is taken over and reported as `lease` in the output. Owner: `MSL_OWNER`, else `CLAUDE_CODE_SESSION_ID`, else `user@host:tty`. `safari stop` releases it.

### Changed

- `safari start` (and `lab up`) never spawn Appium while the LaunchAgent is installed: they load it if needed, wait up to 60 s for it (kicking it once at 30 s), and refuse `--port` other than 4723.
- The liveness check of an Appium session now also needs Safari's page (web context, then `GET /url`), so `safari start` replaces a session whose Safari was killed; a dead session is ended on the server (best effort) before the new one is created, and `safari start` reports `recovered: true`.
- `sim boot` accepts a simulator that is already booting, and its `simctl boot` and `bootstatus` are time-limited (60 s and 300 s).
- `saveState` writes atomically (temp file and rename); `run` takes a `timeoutMs`; `cli` takes `before` and `after` hooks.
- With the LaunchAgent installed, `safari stop` never kills a recorded Appium pid (launchd owns it), `safari start`/`lab up` and `lab service install` clear any stale pid (for example a manual Appium that `--replace` ended), and `safari start --port N` other than 4723 is refused before anything probes N. A port saved with an earlier session is ignored while the service is installed, so `safari start` and `lab up` recover on 4723 instead of being refused.
- `lab service status` warns in `issues` when the plist's `node` is inside a versioned Cellar directory, since a Homebrew upgrade would break the service.

## [0.2.0] - 2026-10-15

### Added

- Appium backend for the simulator (Appium 3.8.0 + XCUITest driver 12.18.1, installed with pnpm in `~/.local/share/msl-appium`, outside this repo): `safari start` launches it on 127.0.0.1 if needed and `safari stop` ends it. [ADR 0002](docs/adr/0002-appium-for-the-simulator.md).

- `safari network`: the network log, with cookie and authorization headers, request bodies and secret URL parameters removed before saving.
- `safari tap`, `keys`, `swipe` and `ui`: real touches and key presses through the native layer (`\b` is Backspace, done by clicking the keyboard's delete key), and Safari's own accessibility tree. `tap` and `swipe` find the page on screen with a temporary probe element (Safari 27 makes the web view fill the screen) and refuse Safari's toolbar and address bar.
- `sim doctor` checks for Appium.

### Changed

- Simulator sessions use Appium; `safaridriver` is now only for `safari start --device <iPhone UDID>`.
- `safari open` waits for the new document to finish loading (a hash-only change waits for the URL instead) and fails after 30 s.
- `safari console` reads Safari's log on the simulator, returns `dropped`, and drops WebDriverAgent entries and exact duplicate messages (Appium delivers one copy per page/native context switch); `safari network` drops the same duplicates; console `url` and `text` get query secrets masked.
- `safari keys` sends one character per call with a 120 ms pause (bulk sends dropped characters mid-word).
- `safari keys` waits 0.7 s for the keyboard to settle before typing, and refuses if it doesn't appear within 3 s.
- Secret query parameters are masked in every `run.log` line (`sim` and `safari`), server error text, the printed `ok: false` JSON, failure artifact errors, stderr notes and the `url` that `open`, `refresh` and `url` print.
- `safari open` to the URL the page is already on returns once the page is loaded instead of timing out.
- `safari tap` and `swipe` refuse (instead of skipping) a native control without a reference.
- `safari eval` returns the value of anything that parses as an expression, including an IIFE containing `return`.
- `safari network` reads the `event` payload of Safari's log entries and leaves out WebDriverAgent's own requests; its redaction also covers relative URLs such as a `Location` header.
- `safari inject` records the file for `--reinject` and notes that it is lost on navigation.
- `sim tap` uses AXe's physical tap style, since the default delivers nothing on Xcode 27.
- `sim boot` reports the `window` it opened.
- `sim doctor` now prints `ok: false`, an `error` and a `hints` object (one fix per missing item) and exits 1 when anything is missing; it was `ok: true` with a `missing` list. The report fields are unchanged apart from the new `appium`.

### Fixed

- `sim create` picked iPhone 11 on Xcode 27, which lists device types newest first; it now picks the highest model number.
- `sim boot` failed without Simulator.app; it opens Device Hub on Xcode 27 and never fails because a window won't open.
- `safari click`, `type` and `tap` found no element: the W3C element key constant was wrong since 0.1 (now `element-6066-11e4-a52e-4f735466cecf`).
- AXe's cold-start failures ("Timed out creating the simulator remote automation session", "No translation object returned for simulator") are retried up to 4 times, 2 s apart.
