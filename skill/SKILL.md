# Mobile Safari testing

**Read `~/repos/mobile-safari-lab/AGENTS.md` at the start of every session that uses the lab.** It is the source of truth and overrides anything you remember or your repo's notes say about the lab (commands, rules, how to report issues).

Real Mobile Safari, on one of two targets:

- **iPhone**: the owner's own phone, over cable or the same Wi-Fi. Real WebKit, GPU, fonts and network, and the owner's extensions and logins.
- **Simulator**: a dedicated iOS Simulator ("Claude iPhone") on the Mac. Clean profile, controllable appearance, no signing, but heavy on a small Mac. A second one, `--profile configured`, holds sign-ins the owner made by hand (see "Profiles" below).

Three tools, all in `~/repos/mobile-safari-lab/bin`, normally on PATH, each printing one JSON object per command:

- **`lab`** gets everything ready and keeps it available: `lab up` checks and repairs the target and the Safari session in one command, `lab down` stops everything the lab started when you're done, `lab status` looks, `lab hold` keeps the idle stop off while a person uses the simulator by hand, `lab release` hands the simulator back, `lab service` manages the Appium LaunchAgent (and the idle stop that stops an idle lab), `lab phone` saves, checks and forgets the iPhone.
- **`safari`** drives the page through Appium on either target: CSS selectors, clicks, real taps and key presses, scrolling, JavaScript, injected userscripts, page source, console and network logs, screenshots.
- **`sim`** drives the simulator itself (open URLs, taps, typing, Safari's own UI). It is refused while the session is on the iPhone.

`~/repos/mobile-safari-lab/AGENTS.md` is the generic version of this workflow, and holds the full **`needs` table** (what each device failure means and the exact steps to relay). `~/repos/mobile-safari-lab/README.md` has setup details.

## Before you start

- **Needs the Mac.** This only works in Claude Code on the Mac. A cloud session can't run `xcrun`: say so, and offer to do the rest when the person is at the Mac.
- **Check the setup.** Run `sim doctor`. If it reports `ok: false`, stop and relay its `hints` (one fix per item in `missing`, including the Appium install command); `~/repos/mobile-safari-lab/README.md` has the setup steps. Never install tools or enable settings without asking. Its `pymobiledevice3` field and `hints.pymobiledevice3` concern Wi-Fi only (the tool must be 11.40.2 or newer) and never make `ok` false: relay that hint only if the task needs Wi-Fi. The lab refuses to run as root, so never prefix it with sudo.
- **Follow the project's own rules.** The project's CLAUDE.md test rules still apply, for example "2023 archive puzzles only" and "leave puzzles unsolved and cleared".

## Pick a target

| Use | When |
| --- | --- |
| `--target device` | The task says iPhone or real device; the owner's extensions, the real WebKit build, GPU, fonts or network matter; the Mac is short on memory. |
| `--target simulator` | A clean, logged-out profile (the default; `--profile configured` only when the task needs a signed-in user the owner set up); dark mode or status-bar control; identical screenshots every run; the phone isn't saved, reachable or unlocked and nobody is there to fix it. |
| `--target auto` (default) | Anything else: the phone when one is saved, reachable and unlocked; the simulator when no phone is saved. A saved phone that can't be used fails with a `needs`; pass `--target simulator` to skip it. |

## Workflow

1. Start a run folder: `sim run <short-label>` (the session started next writes into it), then **`lab up [--target auto|device|simulator] [--profile clean|configured] [--url <url>]`**. It takes the lease, makes sure Appium is up, checks the phone (or boots the simulator), and reuses the Safari session or replaces a dead one. Read its `steps`: each says what it `found` and `did`. Run it again whenever something seems stuck; on a healthy setup it changes nothing.
   - **If the output has `labVersion.human`**, the lab checkout is out of date or not on main: tell the owner those lines as they are, then keep going with the version you have. Never pull or change the checkout yourself, and don't wait for an answer. `labVersion: { checked: false, ... }` just means the check couldn't run (offline, no repository); ignore it. `lab status --check-update` asks GitHub again instead of using the 6-hour cache.
   - **Durations.** iPhone: about 50 s the first time (WebDriverAgent is built and installed), 14 to 18 s warm. Simulator: 22 to 31 s warm, 4 to 10 minutes cold on a loaded 8 GB Mac. The first boot of a new simulator is done by `sim create` (it boots the device once, then shuts it down) and takes up to 25 minutes: run it in the background, not in a foreground command (capped at 10 minutes). A cold `lab up` retries by itself, once, when WebDriverAgent fails to start or Web Inspector lists no pages; if it still fails that way, or with `WebDriver POST /session got no answer in 420s`, the simulator is booted by then, so run `lab up` again (the failed `session` step carries `human` and `then` saying so; stop if the second try fails the same way).
   - **If `lab up` fails with `needs`** (an iPhone problem a person can fix: `setup`, `xcode-account`, `keychain`, `developer-mode`, `trust`, `unlock`, `passcode`, `cable`, `tunnel-tool`, `tunnel`, `resign`, `slots`, `busy`, `tab`, `service`): stop. Relay the `human` steps to the person exactly, then run `then` when they say it's done. The full table is in `~/repos/mobile-safari-lab/AGENTS.md`. If they can't, `or` (`lab up --target simulator`) is the way out; say in your report that the iPhone wasn't tested. Never change the phone's or the Mac's settings yourself.
   - **If `lab up` is refused because the simulator is leased** (`failedStep: "lease"`, naming the owner and expiry): another agent or person is using it. Tell the person who holds it and until when, and wait or ask them. Never run `lab up --force` or `lab release --force` on your own: it takes the simulator from whoever is using it. Do it only after the person says the other agent is done. An expired lease is taken over automatically.
   - Any `sim` or `safari` command takes or renews the lease too, and is refused the same way. `safari stop` releases it.
   - If `lab up` fails at `appium`, `lab service status` shows whether the LaunchAgent is loaded and what is wrong; if it isn't installed, tell the person (`lab service install` is theirs to run).
2. **Page work** (preferred, because it's exact):
   ```sh
   safari open <url>              # waits until the new page has loaded (`lab up --url` already did this)
   safari inject <file.user.js>   # if testing a userscript
   ```
   Then use `safari eval`, `safari click`, `safari shot` and the rest as needed. Check `safari console` for errors and `safari network` for requests. `target` stays the id object; `targetType` (`device` or `simulator`) says which it is. The phone's iOS version is `osVersion` in `lab phone status` or `lab up`'s `phone` block (`lab status` shows the last one as `phone.seen`); Safari's user agent is frozen, so don't use it. `safari help`, `safari <command> --help` (also `sim`, `lab`) print the usage and run nothing.
   - **`eval`:** one expression returns its value; several statements need `return` (`safari eval 'const n = 2; return n'`), else the result is `null`. A page exception comes back as `ok: false` with the page's error, not as a `needs`. A Promise is awaited (`safari eval 'fetch("/x.json").then(r => r.json())'`), for up to `--timeout <ms>` (10 s by default); a rejection, a timeout or a navigation while waiting is `ok: false` with the reason.
   - **Input:** `safari click` and `safari type` are synthetic (`isTrusted` false). `click`, `type` and `tap` also find by visible text, position or open shadow root: `--text "Continue"` (exact, innermost match; `--contains` for part of it; refused when several match until you add `--nth N`, 1-based), `--nth N`, and `--shadow host inner` (all arguments are selectors, the last is the target). `type --text` matches visible text, which an `<input>` has none of: use a css selector for fields. `safari tap --label "<a11y label>"` taps the one native element in the web view with exactly that label (for a closed shadow root or a canvas; labels are in `safari ui`; it never touches Safari's own bars). For what a finger would do, use `safari tap <css>` (scrolls the target into view, focuses a field and brings up the keyboard; check `focused`, and a `warning` means the target is invisible and the tap probably focused nothing; on a cold simulator a tap can take seconds), then `safari keys "text"` (real key presses, auto-capitalisation; `\b` in the text is Backspace, ~0.6 s each in the simulator and up to ~4 s on a self-resetting phone field, so keep runs short; refuses unless a page field is focused; it checks that each character landed and resends it, and if one still doesn't land it fails with `ok: false` naming the character's position (#N) and how many were typed before it (never the text), so never assume text was typed after a failure; `--no-verify` skips the check; put `--` before text that starts with `--`), and `safari swipe up|down` to scroll. `safari ui` lists Safari's own UI labels.
   - **Waiting:** use `safari wait`, not `sleep`. `safari wait '.card' --visible` waits for an element (same selectors as `tap`; plain `wait` is "exists", `--visible` is rendered, `--gone` is removed or hidden); `safari wait --settled` waits until nothing has loaded, changed or resized for `--quiet` ms (500), so run it before `safari shot` on a page that fills in after load; `open` and `refresh` take `--wait-for <css>` and `--settle`. `--timeout` is 10000 ms by default (100 to 60000); a timeout is `ok: false` with counts, not a `needs`. A page that animates constantly never settles: wait for an element instead.
   - **`safari open <url> --storage key=value`** (repeatable, `open` only) sets localStorage on the address's origin before the page loads, for a flag or login state read at start: it writes into the page the tab is already on if that is the same origin, else loads the origin's `/` first (`storage.extraLoad`), writes, then loads the URL. Key 1 to 256 characters, value at most 4096, at most 20 pairs and 16 KiB, no repeated key, no `#fragment`-only change from the current page (the root with a fragment, or the same URL, is set and reloaded); `applied: false` with a `warning` means the page ended on another origin (open the final address). The values are never printed or saved by the lab and a failure after the write saves no `fail.png`; real secrets still don't belong on a command line (shell history, process list; the page can repeat them after the write: title, its own errors, the screen), so use test flags and dummy tokens. `--storage=k=v` and any other `--flag=value`, an unknown or misspelled flag and a second address are refused by position (the pair goes in the next word); `refresh --storage` in any spelling is refused. `--storage` needs the lab's Appium service with current log-filter rules on both targets (no service, older or missing rules, `MSL_APPIUM_URL` set, the service not running or not the listener on its port, or a session on another port is `needs: service`, before anything is sent): the person runs `lab service install`. A service that started before its rules file was last written is refused too, and `type` and `keys` refuse on stale rules before sending anything; once `type` or `keys` has sent its first character a failure saves no `fail.png`/`fail.html` and its message holds no typed text. An Appium started by hand or reached via `MSL_APPIUM_URL` is not checked, so `type` text may be logged there.
   - **`keys` and self-resetting fields.** A character counts as landed when the field's length or text changed or it got a `keydown`/`beforeinput`/`input` event, but events count only while the field has not changed during the run (after that a press that fires events and adds nothing is sent again). A page that resets its input after each key (minutecryptic.com) passes with `byEvent` and `unverified` (and `textSkip: "unverified"` when the field is exactly as it was): the text wasn't seen, so check the page. Such a field costs up to about 1.5 s per character (measured on the phone: about 3 s, and about 4 s per Backspace there; about 1 s per character on a plain input). A plain field whose length ends up short of what was sent after an event-only landing fails ("the field is N characters short"); a longer one is a `warning` only when the text is not compared (password, contenteditable); a readable field the page reformats fails with "the keyboard or the page changed the text".
   - **`keys` reports `caseChanged: true`** (simulator and iPhone) when the keyboard's auto-capitalisation changed only the case (`zq` became `Zq`). That is not a failure; it fails only when the text differs beyond case. `textChecked: false` with a `textSkip` reason says the text wasn't compared (a password field, say).
   - **Never tap or type into Safari's address bar:** typing there and pressing Return performs a web search. `tap` and `swipe` refuse points on Safari's toolbar; don't work around that.
   - **Injected scripts are lost on every navigation and refresh.** After `safari open` or `safari refresh`, run the injection again with `--reinject` (`safari open <url> --reinject`, `safari refresh --reinject`); it re-runs the files `safari inject` recorded whose `@match`/`@include` fit the page it landed on (`@exclude` wins; none means everywhere); the others are listed in `reinjectSkipped`. `safari inject` itself runs anywhere and adds a `warning` when the page doesn't fit. Files stay recorded until dropped: when more than one re-runs (two scripts compared on one site) `open`/`refresh` add a `warning` naming them, and `safari inject --forget <file>` drops one (`--clear` drops all) so only the one under test runs.
   - **`safari network` counts differently per target.** On the simulator `count` is raw events and `requests` is one entry per request; on the iPhone `requests` are the entries and `truncated` covers the rest.
   - **`safari console` and `safari network` drain their buffer** each time they are read. On the simulator both read Safari's log through Appium: `dropped` counts copies and WebDriverAgent's own entries, and `truncated: true` means Appium's 5000-entry buffer filled and earlier entries may be missing (read more often, or `safari stop` then `safari start`). `network` removes cookies, authorization headers, bodies and secret URL parameters (`token`, `key`, `code`, `session`, ...) before saving, but treat `network.json` as sensitive anyway and don't paste it wholesale. On the iPhone, `console` comes from a collector the lab puts in its own tab (it misses what was logged before it was installed) and `network` is the lab page's own Resource Timing, limited to the sites the lab tab visited: `method` and `status` were `null` on every entry on iOS 27.0.1, another site's requests without `Timing-Allow-Origin` show sizes of 0, and a script's own cross-origin calls (and probably `GM_xmlhttpRequest`) only count in `outside`. `dropped` is 0; `truncated` means read again; `lost` and `early` mean entries were missed. Don't `eval` the page's timing entries on the phone to fill the gap: it prints every site the page talked to. For a script's own requests use the simulator.
3. **Phone work** (Safari's toolbar, permission prompts, anything outside the page):
   - **On the iPhone** use `safari shot`, `safari tap`, `safari keys`, `safari swipe` and `safari ui`. The `sim` commands that act on the simulator (`tap`, `type`, `shot`, `ui` and the rest) are refused while the session is on the phone, with a message saying so.
   - **On the simulator** use `sim tap --label`, `sim scroll` and `sim shot`. `sim ui` lists the labels you can tap; to tap a spot you see in a screenshot, use `sim tap X Y --px` with coordinates read off the latest `sim shot`. **While a `safari` session is open, `sim tap` and `sim type` do nothing, silently**; use `safari tap`, `safari keys` and `safari swipe` instead, or `safari stop` first. `sim boot` opens Simulator, or Device Hub on Xcode 27; a missing window is not an error.
4. **Look at your screenshots.** Read the PNGs before saying something works. On the iPhone a plain `safari shot` is the whole screen: it can show the status bar, notifications and the owner's other apps, so don't share it wholesale. `safari shot --page` keeps the web content only (no status bar, no toolbar), `--element <css>` one element (the selectors of `tap`; it doesn't scroll, so the element must be wholly in view), and `--scale 0.5` or `--width 600` shrinks the cut; check `crop` and `points` in the output. A cut that can't be made saves nothing.
5. **Finish with `lab down` when the work is over, `safari stop` for a short break.** `lab down` ends the session and closes the lab's tab (iPhone), stops WebDriverAgent, shuts the simulator down if it was the target, quits the Simulator or Device Hub window only if the lab opened it, stops Appium (the LaunchAgent too, until the next `lab up`) and releases the lease so the next agent isn't kept waiting. On a simulator run it frees about 3 GB, but the next `lab up` is a cold start of 4 to 10 minutes on a loaded Mac, so don't use it between steps of the same job; `safari stop` ends the session, closes the lab's tab and releases the lease while Appium (and the simulator) stay warm. `--keep-service` keeps only the Appium service; it rarely helps. Read its `steps`; if it says `ok: false` the lease is kept, so run it again. If it is refused because another agent holds the lease, don't use `--force` on your own. A cold simulator `lab up` can fail once with Web Inspector listing no pages; it retries by itself, and if it still fails run it again. If you forget, the **idle stop** (a LaunchAgent that `lab service install` adds) does the same as `lab down` once no command that takes, renews or releases the lease (`lab up`, any `safari` command, the `sim` commands that change the phone, `sim shot` and `sim ui`; not `lab status`) has run for 15 minutes, and shuts the simulator down only if the lab booted it; so a break longer than that ends in a cold `lab up`. `lab status` shows `idleStop` (the last stop, `heldUntil`, `nextStop`; `tabLeft` with a `human` step if the phone was unreachable: relay it). **Before you hand the simulator to the person to use by hand, run `lab hold`** (`--minutes N`, 1 to 120, default 60): they run no lab commands, so without it the stop shuts the simulator down under them after 15 minutes. It takes no lease; `lab down` ends it. A lease held by `msl-idle` means the stop is running: retry `lab up` in a minute. Also stop any local server (a dev server for the page, say) that you started yourself, and clean up whatever the project's rules require. `safari start --port` must stay 4723 while the LaunchAgent is installed.

## If a command is interrupted

A command stopped by a signal (Ctrl-C, `kill`, a closed terminal) prints one JSON object with `interrupted` and exits 130, 143 or 129. The session, Appium and the lease are kept. Run `lab status` before the next step. On the phone **a page command already sent may still finish in the lab's tab** (`sessionKept: true`): check the page before you repeat a click or a type. If `tainted` is `true`, run `safari start`. An interrupted `safari stop` or `lab down` did not finish (the session record and lease are kept): run it again.

## The iPhone is the owner's

- The lab opens **its own tab**, pins it and checks it before every command. It never reads or runs anything in another tab (one yes/no check at start, that the attached page is the lab's tab). Never switch tabs on the phone. A command that gets no answer over Wi-Fi is `needs: "tunnel"` (the tunnel or WebDriverAgent does not answer) or `unlock` when that is the cause, and `tab` only when the route works and the phone is unlocked. Switching away only pauses the session (native actions are refused with `needs: "tab"` until the owner switches back; `url`, `eval` and `wait` can be too when Safari pauses the background tab, "did not answer within 10s"; none of this taints the run). A busy page can hold a script up too: the next command that gets no answer says "Appium is still waiting on a script the lab sent to its tab", and `lab status` shows `waitingSince` next to `usable: false`; wait, or run `safari start` if it has not cleared within a minute. The session ends, and `safari start` opens a fresh tab, only when the lab's own tab changes under it (navigated by hand, closed, replaced). **A refused command can still finish in the lab's tab once it shows** (Appium runs one command at a time): after the owner switches back, check the page before you repeat a click or a type. A refused or late script never runs in another tab, and a tab the owner opens does not pull the session into it (Appium runs with the lab's `msl-page-pin` plugin; if `lab status` lists the page pin as missing, or `safari start` is refused with `needs: "service"` about it, relay it and don't run `lab service install` yourself). The one moment it does not cover is session creation: tell the person not to open or switch tabs while `lab up` or `safari start` creates the session. It passed a live check on the phone (iPhone item 19, 2026-10-19). If a command refuses with `needs: "tab"`, relay it. When `safari start` or `lab up` replaces such a session, its `human` (and `previousTab`) asks the owner to close the old lab tab by hand: relay that too; the lab never closes a tab it can't confirm is its own.
- **Safari restarts** when the lab opens its tab: the owner's other tabs reload when next viewed, and unsaved form text in them can be lost. Warn the person before the first run if they may be mid-task.
- `safari stop` and `lab down` close the lab's tab. If the output says `tabClosed: false` (for `lab down`, in `steps[session]`), relay its `human` step (in that step too; close it by hand).
- WebDriverAgent turns the owner's Auto-Correction and Predictive off while a session runs; `safari stop` and `lab down` set them back (`lab phone setup --autocorrection on|off --prediction on|off` changes the target, default both on). If the output says `keyboardRestored: false`, relay its `human` step (turn them on in Settings > General > Keyboard; `keyboardNote` says why); `keyboardDeferred` (a session replaced after a dropped Wi-Fi tunnel) needs nothing from the person: the new session restores them when it ends, and `previousTab` says the old lab tab was left open, which they close by hand; `lab down` says it once (a failed `lab down` keeps it for the retry) and never starts a session for it.
- `safari appearance light|dark` and `safari orientation portrait|landscape` change the owner's phone (iPhone only; a simulator session is refused, `sim appearance` is the simulator's). The lab records the old value first and puts it back at `safari stop`, `lab down`, the idle stop and the next `lab up` after a crash (`restore` does it now; `status` shows the reading and what is pending; `lab up --appearance ... --orientation ...` sets them at start). Always end with `safari stop` or `lab down`. Relay a `human` step: `phoneRestored: false` (phone locked or out of reach; the record is kept and the next `lab up`/`lab down`/`lab phone restore` finishes it), `restoredExactly: false` (Appearance may be on Automatic, which the lab cannot read: it set back light or dark; never say Automatic was kept), or an orientation that "did not change ... Portrait Orientation Lock is probably on" (the person turns the lock off). If the owner changed the setting by hand meanwhile the lab leaves it (`ownerChanged`). Landscape with `shot --page`, `tap` and `swipe` is untested: look at the shot.
- **Lab Focus** (the owner's Focus "Lab", turned on by their shortcut "Lab Focus On"): on by default for a phone `lab up` (a `focus` step before the tab opens; `--no-focus` skips it, `lab phone setup --focus on|off` saves the choice), turned off by "Lab Focus Off" at `safari stop`, `lab down`, the idle stop and `lab phone restore` (the restore ledger, kind `focus`). The lab cannot read which Focus is on, so restores say `restoredExactly: false`; `focus.applied: true` means the shortcut was started (`verified: false`). If `focus` says `applied: false`, relay `human` (the owner makes the Focus, set to silence notifications from all apps, and the two shortcuts; the README has the steps): `lab up` still worked. A locked phone is never launched onto: the record is kept and the next unlocked `lab up`/`lab down`/`lab phone restore` finishes it. The simulator never runs it. `lab phone focus test|off` is the owner's setup check (refused while a session is open).
- **A slot borrowed from sideload** (the owner's sideload shares the phone's few free-account app slots; when the phone is full the lab's `slot` step in `lab up` asks sideload to lend one for WebDriverAgent, and the lab must give it back). **A `lab up` may take about 17 minutes in the `slot` step** for the lend, plus the WebDriverAgent build (first time) and up to two installs: run it in the background and do not start a second one; `needs: busy` with `retryAt` there means sideload is still working, so run `lab up` again after that time. `slot: {lent: "<app>"}` in the result means the owner's app is off the phone until it is given back: say so in your report. Report sideload's data counts if the `slot` carries them (`dataBackedUp`, `dataFiles`, `dataFilesFailed` when lent; `dataRestored`, `dataFilesRestored`, `dataFilesFailed` when given back), and its `warnings`: a failed count means some of the app's data was not backed up or restored. `needs: slots` from the `slot` step (`failedStep: "slot"`) is the owner's to fix (relay `human`; the last line is sideload's own advice). `lab down` and the idle stop give it back on their own (`slot` step; `slotReturned: true`). If the output says `slotReturned: false` or `lab status` shows `slot.lend`, relay its `human` steps (unlock the phone, a stale signing, "another app took the slot"); `lab phone slot return` retries it by hand once the person has done them (refused while a phone session is open). Never run `sideload` yourself, never `lab phone slot forget` (the person returns the slot with sideload first), and never delete an app on the phone.
- The phone must be **unlocked and awake** while you work. If it locks mid-session you get `needs: "unlock"`.
- Off-site redirects are refused. Appium's log redacts page URLs, titles, typed text and storage values at the default `info` level (`--log-level debug` also logs command results, including text read back from fields: debugging only, delete the log after), but **`safari eval` script text reaches that log** (only its arguments are redacted): put sensitive values in `--storage` or typed text, never in eval source, and output masks device ids as `…5F60` (only `lab phone status` and `lab phone setup` print the full UDID; don't paste it).
- A site that sends the lab's tab on to another host (a login, a short link) taints the run unless the person named that host when the session started: `safari start --allow-host <host>` (or `lab up --allow-host <host>`; repeatable, up to 10, exact match, no wildcards). Followed hosts are listed as `followed` in the output. Ask the person which hosts; don't add one to get past a refusal, and note that a taint drops the list.
- `open`/`refresh` retry the tab marking once if the page list moves (`markRetried: true`); a second move is `needs: "tab"`, and the tab left behind may be on the page of the failed command: the output names the last site the lab sent it to.

## Profiles (simulator)

There are two simulators, never booted together. **Clean** is the default for every `lab up`: logged out, no extensions, and `sim reset` makes it new. **Configured** (`lab up --profile configured`, made once by the person with `sim create --profile configured`) keeps the sign-ins and settings the owner made on it by hand, and Safari's data survives from one session to the next. Choose it per `lab up`; it is never sticky. `lab up --profile <other>` while a session is live on the first is refused (`safari stop` first). `sim profile status` shows both devices.

- **Never type a password, a code or any secret into either simulator** (`sim type`, `safari keys`, `safari type`), and never sign in to an Apple ID or iCloud. Signing in on the configured profile is the person's job, by hand in the Simulator window, once. A test account the person names is fine to use for a login the test needs; its password still comes from them typing it, not from you.
- **A shot of a configured session shows what is signed in.** Look at every screenshot before you keep or share it, as on the iPhone, and treat what you see as the owner's data. `console.json`, `network.json` and `fail.html` can hold it too.
- **`sim reset` on the configured profile is refused** without `--profile configured --yes`. Do not add those yourself: they erase the sign-ins for good. Ask the person.
- **A configured session is not pristine.** Cookies, storage and anything installed persist, so reproduce a bug on clean before you report it, and say which profile you used.

## Limits to state in your report

- **Injected scripts start after the page loads.** They don't run at `document-start`, and only `GM_info` is provided. If timing matters, or the script uses `GM_*` storage APIs, say so. On the iPhone other Safari extensions of the owner's can run in the page and change what you see; say whether that could matter.
